# 워치 세션 데이터 — 백엔드 연동 가이드

워치가 기록한 외출 세션을 백엔드가 받아 **장소 추천**으로 만드는 데 필요한 내용을 정리한다.

- 스키마 정의 원본: `core/walksession/.../WalkSessionPayload.kt`
- 설계 근거: `docs/superpowers/plans/2026-07-22-wear-session-transfer.md`
- 이 문서의 실측값은 2026-07-27 갤럭시 워치 실기기 기록에서 나왔다.

**현재 상태:** 워치 → 폰 전송까지 동작한다. 폰 → 백엔드 업로드는 아직 구현 전이며, 5장이 그 제안이다.

---

## 1. 받는 데이터

```json
{
  "clientSessionId": "53e28e1b-844b-4cf5-b7ae-2aa9d8319e73",
  "startedAtEpochMillis": 1785162546953,
  "endedAtEpochMillis": 1785162725582,
  "samples": [
    { "tsEpochMillis": 1785162633019, "lat": null,      "lng": null,       "accuracyMeters": null, "hr": 117.0 },
    { "tsEpochMillis": 1785162633480, "lat": 37.4966959, "lng": 126.9568509, "accuracyMeters": null, "hr": null }
  ],
  "watchMarks": []
}
```

### WalkSessionPayload

| 필드 | 타입 | 의미 |
|---|---|---|
| `clientSessionId` | String (UUID) | 워치가 생성하는 세션 식별자. **업로드 멱등 키로 쓴다** |
| `startedAtEpochMillis` | Long | 사용자가 **시작 버튼을 누른** 시각 (epoch ms) |
| `endedAtEpochMillis` | Long | 사용자가 **종료 버튼을 누른** 시각 |
| `samples` | List | 시간 오름차순 정렬 보장 |
| `watchMarks` | List\<Long\> | 미구현. 항상 `[]` |

`startedAt`/`endedAt`은 **버튼을 누른 시각이지 센서 데이터의 범위가 아니다.** 첫 샘플은 보통 시작보다 10~20초 늦고, 좌표는 그보다 더 늦다(→ 2.4).

### WalkSample

| 필드 | 타입 | 의미 |
|---|---|---|
| `tsEpochMillis` | Long | 센서가 그 값을 관측한 시각 |
| `lat` / `lng` | Double? | WGS84 위경도 (도 단위) |
| `accuracyMeters` | Double? | **현재 항상 `null`** (→ 2.3) |
| `hr` | Double? | 심박 (BPM) |

## 2. 이 데이터의 성질

여기가 이 문서의 핵심이다. 모르고 구현하면 결과가 조용히 틀린다.

### 2.1 위치 행과 심박 행은 분리되어 있다

**한 행에는 위치나 심박 중 하나만 들어 있다.** 위치 행은 `hr`이 `null`이고, 심박 행은 `lat`/`lng`이 `null`이다.

두 센서의 관측 주기와 위상이 달라서 한 행에 합치지 않았다. 억지로 맞추면 없는 정밀도를 지어내는 것이 된다. 실측에서 같은 초의 두 행이 461ms 어긋나 있었다:

```
1785162633019  심박 117
1785162633480  좌표 37.4966959, 126.9568509
```

**그래서:** 심박과 좌표를 엮으려면 시간 기준 근접 매칭(±1초 정도)을 직접 해야 한다. 인덱스로 짝지으면 안 된다.

### 2.2 볼륨

위치·심박 각각 약 1Hz로, **초당 2행**이 쌓인다.

| 세션 길이 | 대략 행 수 |
|---|---|
| 30분 | 3,600 |
| 3시간 | 21,600 |

4시간 세션 기준 원본 JSON 2.8MB, gzip 0.27MB로 측정됐다. 체류 감지 전에 다운샘플링을 고려할 만한 양이다.

### 2.3 `accuracyMeters`는 항상 `null`이다

워치가 아직 채우지 않는다(하드코딩). **정확도 기반 노이즈 필터를 쓸 수 없다.**

**대안:** 연속한 두 좌표의 거리와 시간차로 속도를 구해, 보행에서 불가능한 값(예: 10 m/s 초과)을 이상치로 버린다. 도심에서 GPS가 튀는 경우를 이걸로 대부분 걸러낼 수 있다.

워치 쪽에서 채우는 작업이 예정돼 있다(→ 6장).

### 2.4 세션 초반에는 좌표가 없다 — 콜드 스타트

GPS 첫 측위(TTFF)에 시간이 걸린다. 같은 기기·같은 장소 실측:

| 상황 | 첫 측위까지 |
|---|---|
| 콜드 (오래 안 쓴 상태) | **84초** |
| 핫 (직전에 썼던 상태) | **1.2초** |

**그래서 출발지는 기록되지 않는 경우가 많다.** 세션의 첫 좌표를 "집에서 나온 지점"으로 해석하면 안 된다. 실제로는 이미 1~2분 걸어간 지점이다.

### 2.5 좌표가 끊기는 구간

두 경우를 나눠서 다룬다.

#### (a) 세션 전체에 좌표가 0개 — 분석하지 않는다

측위에 실패한 세션이다. 실제로 **31분 내내 좌표가 0개이고 심박만 1초 간격으로 들어온** 세션이 나온 적이 있다.

**이건 워치 쪽 결함이지 백엔드가 보정할 수 있는 문제가 아니다.** 심박만으로는 장소를 만들 수 없으므로 **추천 대상에서 제외한다.**

다만 **집계는 남기는 것을 권한다.** 이런 세션의 비율이 올라가면 워치에 문제가 생겼다는 신호이고, 그게 앱 쪽에서 가장 빨리 알아챌 수 있는 경로다.

#### (b) 세션 중간의 공백 — 전후 좌표로 판단한다

실내나 지하로 들어가면 GPS가 끊긴다. 이걸 체류로 오해하면 지하철 이동 구간이 장소 추천에 올라온다.

**공백 직전과 직후 좌표의 거리**가 가장 직접적인 신호다:

| 공백 전후 거리 | 해석 | 처리 |
|---|---|---|
| 가깝다 (예: 100m 이내) | 그 자리에 머물렀다 | 체류 후보로 이어붙인다 |
| 멀다 | 이동했다 (지하철·버스) | 체류 아님 |

심박은 여기서 보조로만 쓴다 (→ 4장).

현재 페이로드에는 "왜 끊겼는지"가 담기지 않는다(→ 6장).

### 2.6 심박이 좌표보다 먼저, 그리고 오래 들어온다

같은 세션에서 심박은 시작 +20.9초, 좌표는 +86.5초에 시작됐다. 실내에서도 심박은 계속 들어온다.

**즉 심박은 세션 전 구간을 덮지만 좌표는 아니다.** 두 신호의 커버리지가 다르다는 걸 전제로 설계해야 한다.

## 3. 처리 파이프라인

좌표 수천 개에서 의미 있는 장소 몇 개를 뽑아 추천까지 가는 흐름이다.

```
원시 세션
  → [0] 전처리
  → [1] 체류 감지
  → [2] 심박 특징 추출
  → [3] 카카오 장소 매칭
  → [4] 스코어링·추천
```

| 단계 | LLM 필요? |
|---|---|
| 0. 전처리 | 불필요 |
| 1. 체류 감지 | 불필요 — 규칙으로 충분하다 |
| 2. 심박 특징 | 불필요 |
| 3. 장소 매칭 | 1차는 규칙. **후보가 애매할 때 도움** |
| 4. 스코어링·추천 | **유력** — 특히 추천 문구 생성 |

LLM을 아직 정하지 않았다면 **0~2단계를 먼저 규칙으로 만들면 된다.** 그 결과물이 있어야 3·4단계에서 LLM에 넘길 입력이 생긴다.

### [0] 전처리

1. **좌표가 0개면 여기서 끝낸다** — 분석 대상에서 빼고 집계만 남긴다 (→ 2.5a)
2. 위치 행만 뽑아 궤적을 만든다
3. 속도 이상치를 제거한다 (→ 2.3)
4. 좌표 공백 구간을 찾아 전후 좌표 거리로 체류/이동을 표시한다 (→ 2.5b)

### [1] 체류 감지

**반경 + 시간** 기준의 고전적인 stay point 검출로 충분하다.

> 연속한 좌표들이 반경 `R` 안에 `T` 이상 머물면 하나의 체류로 묶는다.

초기값 제안: `R = 50m`, `T = 5분`. 실데이터로 조정이 필요하다.

출력: `{ 중심좌표, 시작시각, 종료시각, 지속시간 }`

주의할 것:
- 세션 첫 구간은 좌표가 없으므로 체류가 안 잡힌다 (→ 2.4)
- 공백 전후 좌표가 가까우면 그 공백은 하나의 체류로 이어붙인다 (→ 2.5b)

### [2] 심박 특징 추출

절대 BPM은 사람마다 달라 그대로 쓰면 안 된다. **세션 안에서 정규화한다.**

1. 세션 기저심박 = 그 세션 심박값의 하위 20 백분위수
2. 체류 구간마다: 평균 심박, 기저 대비 비율, 안정화까지 걸린 시간

용도는 4장에 정리했다.

### [3] 카카오 장소 매칭

체류 중심좌표로 카카오 로컬 API를 호출한다. 한 좌표에 후보가 수십 개 나오므로 좁혀야 한다.

좁히는 순서:
1. **거리** — 체류 중심에서 가까운 순
2. **체류 유형** — 정적이면 카페·식당·서점 쪽, 동적이면 쇼핑몰·체육시설 쪽 (→ 4장)
3. **체류 시간** — 3분 체류에 영화관은 맞지 않는다
4. **시간대** — 오전 8시의 술집은 후보에서 뺀다

1~4로도 대부분 하나로 좁혀진다. **끝까지 애매한 경우에만 LLM에 후보 목록과 맥락을 넘겨 고르게 하는 것을 권한다.** 처음부터 LLM에 맡기면 비용만 늘고 정확도는 규칙보다 낫지 않다.

### [4] 스코어링·추천

체류 시간, 재방문 횟수, 시간대, 심박 특징을 합쳐 점수를 낸다. 추천 문구를 자연어로 만드는 단계는 LLM이 적합하다.

## 4. 심박을 어디에 쓸 것인가

### 쓸 것

**① 체류 확신도 보강**

GPS만으로는 신호등 대기 90초와 카페 3분이 잘 구분되지 않는다. 심박이 기저 수준으로 **떨어져서 유지되면** 실제로 앉아 쉰 것이고, 걷기 수준을 유지하면 잠깐 멈춘 것이다.

**② 체류 유형 태깅**

기저 대비 심박으로 정적/동적을 가른다. 3단계에서 카카오 후보를 좁히는 데 쓴다.

| 기저 대비 | 유형 | 어울리는 카테고리 |
|---|---|---|
| 낮음 (기저 근처) | 정적 | 카페, 식당, 서점 |
| 높음 | 동적 | 쇼핑몰, 체육시설, 등산로 |

경계값은 실데이터로 정해야 한다.

**③ 공백 구간 보조 판별** (→ 2.5b)

1차 판단은 공백 전후 좌표 거리로 한다. 심박은 그 위에 얹는 보조 신호다 — 전후 좌표가 가까운데 그동안 심박이 걷기 수준이었다면, 한자리에 앉아 있었다기보다 건물 안을 돌아다닌 쪽에 가깝다.

### 쓰지 말 것

**감정·선호도 추정은 권하지 않는다.** "심박이 올랐으니 이 장소를 좋아했다" 같은 추론은 근거가 약하다.

- HRV(심박변이도) 없이 평균 BPM만 있다
- 걷다가 멈추면 어차피 떨어지는 값이라 흥미와 구분되지 않는다
- 계단·경사·날씨·카페인에도 똑같이 움직인다

추천 품질을 올리기보다 노이즈를 넣게 된다. 심박은 **"어떤 상태로 머물렀나"를 보조하는 신호**로만 쓰고, 선호도는 재방문·체류시간처럼 행동으로 드러나는 값에서 뽑는 편이 낫다.

## 5. API 계약 제안

아직 구현 전이다. 백엔드와 합의하고 앱에 반영한다.

```
POST /api/v1/walk-sessions
Content-Type: application/json
Content-Encoding: gzip
```

본문은 1장의 페이로드 그대로다.

**멱등성** — `clientSessionId`에 유니크 제약을 건다. 워치는 전송에 실패하면 세션을 보관했다가 재시도하므로 **같은 `clientSessionId`가 여러 번 올 수 있다.** 이때 새로 만들지 말고 기존 결과를 그대로 돌려준다.

**압축** — 샘플이 수천 개라 gzip이 필수에 가깝다. 워치→폰 구간에서 이미 gzip을 쓰고 있고, 4시간 세션이 0.27MB로 줄었다.

**크기 한도** — 워치→폰 구간에는 압축 4MB / 해제 32MB 한도가 걸려 있다(`WalkSessionJson`). 백엔드도 비슷한 상한을 두는 것을 권한다.

**응답** — 세션 ID와 처리 상태 정도면 충분하다. 분석은 비동기로 돌리고 결과는 별도 조회로 가져가는 편이 낫다. 3시간 세션의 체류 감지와 카카오 호출을 요청 안에서 끝내기는 어렵다.

## 6. 미해결 항목

앱 쪽에서 예정된 작업이다. 백엔드 설계 시 **곧 생길 필드**로 감안해 둔다.

| 항목 | 현재 | 예정 |
|---|---|---|
| `accuracyMeters` | 항상 `null` | 실제 측위 오차(m)를 채운다. 노이즈 필터 정확도가 올라간다 |
| 좌표 공백 사유 | 전달 안 됨 | `locationSpans`로 "언제부터 언제까지 측위 불가였는지"를 싣는다. 2.5b의 판별을 추측 없이 할 수 있게 된다 |
| `watchMarks` | 항상 `[]` | 사용자가 워치에서 직접 지점을 표시하는 기능. 우선순위 낮음 |

세 필드 모두 **기본값이 있어 추가돼도 기존 파싱은 깨지지 않는다.**
